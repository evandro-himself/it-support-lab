# SD-003 — SQL básico aplicado à investigação de suporte

**Status:** demonstração documental preparada; execução em banco de dados pendente  
**Natureza:** cenário fictício com dados de exemplo; não houve consulta a banco corporativo real.

## Objetivo

Demonstrar como um analista N1 pode interpretar consultas SQL simples, investigar registros e encaminhar evidências ao N2 sem alterar dados de produção.

## Cenário simulado

Um usuário informa que não encontra seu pedido no sistema. A equipe de suporte precisa verificar se o registro existe e qual seu status.

## Estrutura fictícia

Tabela `pedidos` com campos `id`, `cliente`, `status`, `data_criacao`.

| id | cliente | status | data_criacao |
| --- | --- | --- | --- |
| 1001 | Cliente Alfa | PROCESSANDO | 2026-10-20 |
| 1002 | Cliente Beta | CONCLUIDO | 2026-10-21 |
| 1003 | Cliente Alfa | PENDENTE | 2026-10-22 |
| 1004 | Cliente Gama | CANCELADO | 2026-10-23 |

## Consultas didáticas

**Localizar um pedido específico:**

```sql
SELECT id, cliente, status, data_criacao
FROM pedidos
WHERE id = 1003;
```

**Listar pedidos pendentes:**

```sql
SELECT id, cliente, status
FROM pedidos
WHERE status = 'PENDENTE'
ORDER BY id;
```

**Contar pedidos por status:**

```sql
SELECT status, COUNT(*) AS quantidade
FROM pedidos
GROUP BY status
ORDER BY quantidade DESC;
```

## Resultado esperado com os dados fictícios

- Pedido 1003: Cliente Alfa, status PENDENTE.
- Um pedido PENDENTE, um PROCESSANDO, um CONCLUIDO e um CANCELADO.

Estes resultados são deduzidos da tabela acima, **não são saídas capturadas de uma execução SQL**.

## Conduta profissional

- Priorizar acesso de **somente leitura**, quando autorizado.
- Não executar `UPDATE`, `DELETE` ou `DROP` em produção para solucionar incidentes sem autorização e procedimento formal.
- Evitar consultas desnecessárias a dados pessoais.
- Registrar consulta, contexto, horário e resultados sem expor dados sensíveis.
- Encaminhar inconsistências à equipe responsável pelo banco ou aplicação.
